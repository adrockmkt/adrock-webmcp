# v0.6 Content Retrieval Architecture

Status: arquitetura aprovada em 23 de setembro de 2026.

Data: 23 de setembro de 2026.

## Contexto

A v0.5 validou dynamic content discovery. No benchmark, WebMCP recuperou artigo relevante em 6/6 perguntas e referência do gold set em 5/6.

A limitação observada em C-Q2 foi diferente: `search_blog` localizou os documentos corretos, mas retorna apenas metadata. O agente então extrapolou detalhes que não estavam no contexto recebido.

A v0.6 deve resolver retrieval e grounding sem alterar a responsabilidade de `search_blog`.

## Objetivo

Adicionar uma tool read-only que permita ao agente recuperar conteúdo público normalizado de um artigo previamente descoberto:

```text
search_blog({ query })
    ↓
slug
    ↓
get_blog_article({ slug })
    ↓
conteúdo público do artigo
    ↓
síntese grounded
```

## Princípios

1. Discovery e retrieval permanecem separados.
2. `search_blog({ query })` mantém o contrato validado na v0.5.
3. Somente conteúdo público de `adrock.com.br/blog/*` pode ser recuperado.
4. A tool não executa actions, escrita, formulários ou chamadas autenticadas.
5. O navegador do visitante não deve fazer scraping arbitrário do site a cada pergunta.
6. O artefato deve continuar compatível com o loader pequeno do Framer e runtime externo.
7. Conteúdo retornado deve ser determinístico, sanitizado e limitado.

## Arquitetura proposta

```text
Framer CMS
    ↓ publish
adrock.com.br/blog/*
    ↓ scheduled/build sync
article extractor
    ↓
normalized article store
    ↓
GitHub Pages runtime/data
    ↓
get_blog_article({ slug })
    ↓
WebMCP agent
```

A extração acontece no pipeline controlado, não sob demanda no navegador do visitante.

## Contrato proposto

Nome:

`get_blog_article`

Input:

```json
{
  "slug": "ga4-mcp-google-analytics-mensuracao-ia"
}
```

Schema:

- `slug`: string obrigatória
- `additionalProperties: false`

Output conceitual:

```json
{
  "slug": "...",
  "url": "...",
  "title": "...",
  "description": "...",
  "category": "...",
  "published_at": "YYYY-MM-DD",
  "content": "...",
  "content_length": 12345,
  "truncated": false
}
```

O formato final será congelado após os testes de extração.

## Conteúdo normalizado

O extractor deve priorizar o corpo editorial do artigo e excluir, quando identificável:

- navegação;
- header/footer;
- menus;
- CTAs globais repetidos;
- conteúdo de páginas relacionadas;
- scripts e estilos;
- elementos de interface do Framer.

Deve preservar estrutura textual útil, como títulos, subtítulos, parágrafos, listas e links relevantes, em representação textual compacta.

## Segurança

`slug` nunca será convertido diretamente em URL arbitrária.

Fluxo obrigatório:

```text
slug recebido
    ↓
lookup no catálogo gerado
    ↓
registro conhecido?
    ├── não → erro controlado
    └── sim → retornar somente artefato previamente extraído
```

Isso impede que a tool seja transformada em proxy de fetch/SSRF ou leitor genérico de URLs.

Nenhum HTML executável será retornado como código ativo.

## Limites

O conteúdo integral pode exceder o contexto útil de alguns agentes. A primeira implementação deve medir tamanhos reais antes de definir o limite final.

Se truncamento for necessário:

- deve ser determinístico;
- `truncated` deve ser explícito;
- início e fim não podem produzir JSON inválido;
- não deve inventar resumo para substituir texto removido.

Paginação/chunks só serão introduzidos se os dados reais justificarem a complexidade.

## Delivery

A preferência é reutilizar GitHub Pages e o pipeline já validado.

Possíveis artefatos:

```text
public/
  blog-search.js
  blog-articles.json ou artefatos por slug
  adrock-webmcp.js
  search-blog-tool.js
  get-blog-article-tool.js
```

A escolha entre um catálogo único e arquivos por slug será feita após medir tamanho total e distribuição dos artigos.

Não embutir todo o corpus no Custom Code do Framer.

## Cache e atualização

O pipeline deve continuar baseado na superfície pública publicada.

Novo conteúdo ou alteração editorial deve:

```text
publish Framer
    ↓
sync
    ↓
detectar mudança
    ↓
reextrair conteúdo necessário
    ↓
publicar artefato
    ↓
runtime consumir versão atualizada
```

A v0.6 deve medir e documentar comportamento de cache dos assets externos. Cache busting/versionamento será adotado se necessário com base no teste.

## Error handling

Casos mínimos:

- slug ausente ou inválido;
- slug desconhecido;
- artefato indisponível;
- registro sem conteúdo extraível;
- runtime externo indisponível;
- browser sem `document.modelContext`.

Falhas devem ser explícitas e não causar registro parcial ou resposta silenciosamente incorreta.

## 0.6.2 Corpus Size Analysis: validated

Validated on 2026-09-23 against the current generated index.

Observed corpus:
- articles analyzed: 241
- successful extractions: 241
- extraction failures: 0
- total normalized content: 915,328 characters / 944,940 UTF-8 bytes
- average: 3,798 characters
- P50: 3,197 characters
- P75: 4,653 characters
- P90: 5,847 characters
- P95: 8,043 characters / 8,332 bytes
- P99: 26,909 characters
- maximum: 29,295 characters / 30,221 bytes

Architecture decision for 0.6.3:
- use one deterministic artifact per known article slug;
- keep a small generated catalog/manifest for closed slug lookup;
- do not load the full article corpus into the visitor browser;
- do not truncate articles at the current observed maximum;
- preserve an explicit content length field and revisit limits if future corpus measurements materially exceed the observed distribution.

Rationale:
The complete corpus is under 1 MB, so a monolithic artifact is technically possible, but it would transfer hundreds of unrelated articles to satisfy a single retrieval. Per-slug artifacts keep retrieval proportional to the requested article and preserve the security model in which only generated known slugs can be read.

0.6.2 gate: PASSED.

## 0.6.4 get_blog_article Tool: validated

Validated on 2026-09-23.

Evidence:
- focused tests: 5/5 passed;
- retrieval is restricted to canonical slugs present in the generated manifest;
- unsafe path-like input is rejected before any network request;
- unknown valid slugs fail closed after manifest lookup and do not trigger an article fetch;
- manifest paths must exactly match `blog-articles/<slug>.json`;
- returned artifacts are checked against the requested slug and manifest URL;
- tool contract is read-only, requires only `slug`, and rejects additional properties;
- registration fails safely when WebMCP or the retrieval runtime is unavailable.
